Gestion des transactions avec Spring Data JPA

Objectif

Définir les bonnes pratiques de gestion des transactions dans les applications Spring Boot utilisant Spring Data JPA afin de garantir :
	•	la cohérence des données
	•	la performance
	•	la lisibilité du code
	•	la séparation claire entre couche repository et couche service
	•	la robustesse des opérations de lecture et d’écriture

⸻

Principe général

Dans Spring Data JPA, les méthodes héritées de CrudRepository / JpaRepository sont déjà transactionnelles par défaut.

Cependant, ces transactions sont limitées à chaque appel de repository.

La couche service doit définir la transaction métier globale.

⸻

Fonctionnement par défaut de Spring Data JPA

Spring Data JPA utilise l’implémentation SimpleJpaRepository.

Méthodes de lecture

Les méthodes suivantes sont configurées avec :

@Transactional(readOnly = true)

Exemples
	•	findById
	•	findAll
	•	existsById
	•	count
	•	findAllById

Cela signifie :
	•	ouverture d’une transaction
	•	session Hibernate active
	•	optimisation read-only
	•	fermeture après la requête

Chaque appel est isolé.

⸻

Méthodes d’écriture

Les méthodes suivantes sont configurées avec :

@Transactional

Exemples
	•	save
	•	saveAll
	•	delete
	•	deleteById

Cela garantit :
	•	transaction
	•	flush
	•	rollback possible

⸻

Limite des transactions repository

Chaque appel de repository ouvre sa propre transaction.

Exemple :

User user = userRepository.findById(id);
List orders = orderRepository.findByUserId(id);

Cela provoque :

transaction 1
→ find user
transaction fermée

transaction 2
→ find orders
transaction fermée

Il n’y a pas de transaction globale.

Cela peut provoquer :
	•	incohérences
	•	LazyInitializationException
	•	perte de cohérence métier

⸻

Rôle de la couche service

La couche service doit définir la transaction globale.

Exemple :

@Transactional(readOnly = true)
public UserProfile getProfile(Long id) {

User user = userRepository.findById(id);
List<Order> orders = orderRepository.findByUserId(id);

return new UserProfile(user, orders);

}

Ici :

1 transaction globale

find user
find orders
mapping DTO

transaction fermée

Cohérence garantie.

⸻

Règles de bonnes pratiques

1. Ne pas mettre de transaction dans les repositories

Les repositories Spring Data sont déjà transactionnels.

Interdit :

@Repository
@Transactional
public interface UserRepository

⸻

2. La transaction se définit dans le service

La couche service porte la logique métier.

Donc :

@Service
@Transactional(readOnly = true)
public class UserService

⸻

3. Lecture simple

Autorisé sans transaction explicite.

Exemple :

public User getUser(Long id) {
return userRepository.findById(id);
}

Car Spring Data ouvre déjà une transaction read-only.

⸻

4. Lecture métier

Transaction recommandée.

Cas :
	•	plusieurs requêtes
	•	mapping DTO
	•	lazy loading
	•	logique métier
	•	agrégation
	•	pagination
	•	cohérence nécessaire

Exemple :

@Transactional(readOnly = true)
public UserProfile getProfile(Long id)

⸻

5. Écriture

Transaction obligatoire.

Exemple :

@Transactional
public void createUser(User user)

⸻

Cas d’utilisation de readOnly

Plusieurs requêtes

@Transactional(readOnly = true)

permet :
	•	cohérence
	•	même transaction
	•	même snapshot

⸻

Lazy loading

@Transactional(readOnly = true)

permet :
	•	session Hibernate active
	•	chargement des relations
	•	évite LazyInitializationException

⸻

Mapping DTO

@Transactional(readOnly = true)

permet :
	•	chargement des relations
	•	transformation sécurisée

⸻

Logique métier

@Transactional(readOnly = true)

permet :
	•	cohérence des décisions
	•	isolation des lectures

⸻

Agrégation

@Transactional(readOnly = true)

permet :
	•	cohérence des données
	•	snapshot stable

⸻

Configuration Hikari

La configuration suivante est déconseillée :

spring.datasource.hikari.read-only=true

Car :
	•	impact sur les écritures
	•	confusion
	•	Spring gère déjà le read-only

Utilisation recommandée uniquement pour :

read replica

⸻

Repository

interface UserRepository extends JpaRepository

Service

Résumé

Les repositories Spring Data sont transactionnels par défaut.

Cependant :

la transaction globale doit être définie au niveau service.

readOnly permet :
	•	cohérence
	•	performance
	•	session Hibernate active
	•	isolation

La règle :

transaction au niveau service, jamais au niveau repository.
